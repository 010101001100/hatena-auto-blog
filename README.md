# はてなブログ 高品質自動投稿

GitHub Actionsで1日1回、**テーマ選定 → 公式資料の調査 → 執筆 → 編集・完走性・公式根拠の監査 → はてなブログ公開**まで自動化します。

## 現在の構成

- 実行: 毎日 08:17（Asia/Tokyo）。無料枠の消費を抑えるため1日3回から変更
- 標準モデル: Gemini 3.8 Flash
- 公式資料の直接取得を必須とする（GeminiのGoogle検索グラウンディングは既定で無効）
- 検索ソースが2件未満なら、その回は投稿しない
- 直近最大50記事と比較して重複テーマを抑制
- 記事は1600〜3500字を目安（手順の欠落を優先して是正し、文字数で水増ししない）
- 参考情報セクションと参照リンク2件以上を必須化
- 100点満点（正確性25・検索意図20・実用性20・構成15・タイトルSEO10・独自性10）で90点以上を要求
- 全項目4/5以上、具体性4/5以上、事実リスクなし、公式根拠との整合監査PASS、読者の操作完走性監査PASSを同時に要求
- 不合格なら1テーマ最大2稿、原則1テーマだけを生成・再評価（API無料枠を節約）
- 品質基準を満たさない場合やAPI呼び出し枠を使い切った場合は投稿しない
- PRとmainへのコードpush時はテストのみ実行し、投稿処理は起動しない
- 定期実行と手動実行時のみ、テスト合格後に公開処理へ進む
- Gemini APIは1実行14リクエストを上限とし（環境変数 `MAX_GEMINI_CALLS`）、日次クォータ超過のモデルは当該実行中再利用しない
- APIの内部・外部二重リトライを解消。HTTP 503など一時エラーだけ1回再試行し、日次429は再試行しない
- 調査時のGemini 1回で実行計画（前提条件・操作順・成功判定・失敗時の分岐）まで生成し、計画を初稿へ必ず渡す。計画が不完全なら執筆を開始しない
- 最初の原稿で必要な操作を完成させ、形式・必須手順をローカル確認してから採点AIを呼ぶ。採点で不合格なら高コストな追加監査を省略

## 標準ジャンル

BLOG_THEME未設定時は以下に絞ります。

- Windows・PowerShell・CLI
- Python・開発環境
- Git・GitHub
- yt-dlp・FFmpeg
- VS Code・Docker

医療・法律・投資・税務・危険作業、副業一般論、芸能・雑記は自動記事の対象外です。

## 品質チェック

公開前に以下を確認します。

1. 検索意図との一致
2. 具体性・再現性
3. 調査根拠との整合性
4. 構成・読みやすさ
5. 実用性
6. 過去記事との差別化
7. タイトル/SEOと検索語の自然な一致
8. 前提条件、ファイル作成、コマンド入力場所、期待結果などの完走性

機械チェックでは、本文長、見出し数、手順/箇条書き、AI定型句、既存タイトル類似度、参考リンク数も検査します。

**品質より投稿本数を優先しません。**
検索が失敗したり、根拠が薄かったり、QAに落ちた日は投稿なしになります。

## 必須 Secrets

GitHubの Settings → Secrets and variables → Actions → Secrets に登録:

- GEMINI_API_KEY
- HATENA_ID
- HATENA_BLOG_ID
- HATENA_API_KEY

以前の設定でGemini APIキーを OPENAI_API_KEY という名前に保存している場合も、互換性のためそのまま動きます。
新しく整理する場合は GEMINI_API_KEY を推奨します。

## 任意 Variables

- BLOG_THEME — ブログの方向性を上書き

## ファイル

- quality_v2.py — 調査・執筆・品質判定・はてな投稿の本体
- quality_runner.py — 公式資料監査、操作完走性監査、モデルフォールバック、追加品質ガード
- quality_gate.py — 100点採点と独立監査のハードゲート
- article_checks.py — SSH接続確認・Pythonのファイル作成など、完走性の自動検査
- execution_plan.py — 公式情報に基づく初稿の完走計画の検証・プロンプト化
- tests/ — 公開判定が甘くならないための回帰テスト
- quality_entry.py — JSON崩れ時の再試行
- .github/workflows/auto-post.yml — 1日1回の実行設定
- main.py — 旧バージョン（現在は実行されません）

## 投稿を止める

Actions → Hatena Auto Blog → Disable workflow で停止できます。

GitHub Actionsのscheduled workflowは、GitHub側の混雑で開始時刻が遅れる場合があります。
